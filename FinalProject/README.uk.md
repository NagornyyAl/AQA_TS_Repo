# Practice Software Testing - Playwright framework

[English](README.md) | **Українська**

TypeScript-фреймворк автоматизації тестування на базі **Playwright Test** для застосунків Practice Software Testing.

Основний набір тестів покриває два публічні ресурси:

- поточний UI: [Practice Software Testing](https://practicesoftwaretesting.com/);
- окремий API-ресурс: [Toolshop API v2](https://api-v2.practicesoftwaretesting.com/api/documentation).

Поточний UI — новіший застосунок, який всередині використовує `https://api.practicesoftwaretesting.com`. Фреймворк перехоплює ці браузерні API-відповіді для інтеграційних перевірок UI/API. API v2 тестується як окремий самостійний API-ресурс; він не розглядається як бекенд поточного UI.

## Що покрито

- E2E поточного UI: каталог, фільтрація за категоріями, пошук, сортування за ціною, деталі товару, супутні товари та збільшення кількості.
- Інтеграція UI/API: відображені значення та порядок порівнюються з фактичними відповідями `QUERY` і `GET`, які спостерігає браузер.
- API v2: пагінація, Zod-контракти, узгодженість списку/деталей, фільтрація за категоріями, сортування, регістронезалежний пошук, супутні товари та негативна обробка `404`.
- Контракти: Pact V3 consumer-контракт для API v2 плюс верифікація проти публічного провайдера.
- Докази реальних дефектів на обраному UI-ресурсі: скриншоти, відео, трейс, expected/actual та API-обміни.
- Опційна, повністю окрема демонстрація на офіційному навмисно зламаному середовищі `with-bugs`.
- Шаруваті Playwright-фікстури, компонентні Page Object'и, типізовані клієнти, Zod-контракти для конкретних ендпоїнтів і перевикористовувані сервіси репортингу.

Дійсні ID товарів на поточному UI — це ULID, і вони можуть змінюватися під час оновлення публічних даних. Тому позитивні тести знаходять актуальний товар динамічно з каталогу замість покладання на жорстко закодований URL товару.

## Підтверджені дефекти на обраному ресурсі

Відомий застарілий URL товару (його ULID більше не існує в публічному каталозі) наразі виявляє два відтворювані дефекти:

| ID             | Фактичний результат                                               | Очікуваний результат                                                                                |
| -------------- | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `LIVE-API-001` | Ендпоїнт товару повертає `404`, але `/related` повертає `500`.    | Супутні товари для відсутнього товару повертають клієнтський `404`, а не внутрішню помилку сервера. |
| `LIVE-UI-001`  | Сторінка частково порожня, але все ще показує `Related products`. | Показується зрозумілий стан `Product not found`.                                                    |

Обидва тести позначені як очікувані падіння (`test.fail()`): поки дефекти існують, основний прогін залишається зеленим і водночас фіксує всі докази (скриншоти, відео, трейс та API-обміни). Щойно дефект виправлять на публічному сайті, відповідний тест повідомить про неочікуване проходження і має бути перетворений на постійне регресійне покриття.

Попереднє твердження про кількість не є дефектом обраного ресурсу. `UI-PROD-002` тепер перевіряє коректну поточну поведінку: кількість змінюється з `1` на `2`.

## Структура проєкту

```text
src/
  api/          # Типізований клієнт API v2
  config/       # Основне середовище та середовище опційної демонстрації
  contracts/    # Zod-контракти виконання для конкретних ендпоїнтів
  fixtures/     # Шаруваті фікстури сервісів, API та сторінок
  models/       # Моделі відповідей API v2
  pages/        # Page Object'и та UI-компоненти
  reporting/    # Вкладення контексту, результату, API та скриншотів
tests/
  api/          # Автономні перевірки API v2
  contracts/    # Pact consumer і верифікація провайдера
  e2e/          # Поточний UI, інтеграційні перевірки та дефекти обраного ресурсу
  defects/      # Опційна демонстрація with-bugs; виключена з основного конфігу
```

## Стратегія тестування

Тести працюють лише на читання і не створюють, не змінюють і не видаляють публічні дані.

| Шар                      | Покриття                                                                                                              |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| API v2                   | Транспорт, схеми, пагінація, узгодженість, фільтрація, сортування, пошук, супутні товари та негативні відповіді.      |
| Поточний UI              | Навігація, каталог, фільтри, пошук, сортування, деталі товару та поведінка кількості.                                 |
| Інтеграція               | Тіло браузерного запиту та відповідь додаються як вкладення; картки/деталі UI порівнюються з живим API UI-застосунку. |
| Контракти                | Pact-матчери на рівні полів і верифікація проти провайдера API v2.                                                    |
| Дефекти обраного ресурсу | Справжні падіння саме на застарілому ресурсі товару, з відтворюваними доказами.                                       |
| Опційна демонстрація     | Чотири навчальні падіння на окремих навмисно зламаних UI/API-хостах.                                                  |

Тести використовують ID на кшталт `API-PROD-004`, `UI-CAT-003`, `LIVE-API-001` і теги, зокрема `@api`, `@e2e`, `@smoke`, `@regression`, `@integration`, `@negative`, `@defect` та `@known-bug`.

## Установлення

```bash
corepack enable
pnpm install
pnpm exec playwright install chromium firefox webkit
```

## Основний запуск на обраному ресурсі

```bash
pnpm run test
```

Цільові команди:

```bash
pnpm run test:api
pnpm run test:e2e
pnpm run test:contract
pnpm run test:smoke
pnpm run test:regression
pnpm run typecheck
```

## Якість коду

ESLint і Prettier використовують спільний стиль конфігурації репозиторію (`eslint.config.mjs`, `.prettierrc`):

```bash
pnpm run lint
pnpm run lint:fix
pnpm run format:check
pnpm run format
```

## Крос-браузерне покриття

`pnpm run test` запускає три Playwright-проєкти: `chromium`, `firefox` і `webkit`. Лише `chromium` виконує повний набір (API, E2E, контракти); `firefox` і `webkit` обмежені лише `tests/e2e`, оскільки API/контрактні тести працюють з HTTP-ендпоїнтами напряму і нічого не виграють від повторного запуску в кожному браузері. Щоб запустити один браузер локально:

```bash
pnpm run test:chromium
pnpm run test:firefox
pnpm run test:webkit
```

`playwright.with-bugs.config.ts` явно фіксує власний проєкт лише з `chromium`, тому опційна демонстрація дефектів ніколи не успадковує мультибраузерну матрицю базового конфігу.

Відкрити основний Playwright-звіт:

```bash
pnpm run report
```

Основні результати:

- `playwright-report/` - інтерактивний HTML-звіт;
- `test-results/results.json` і `test-results/junit.xml`;
- `test-results/` - скриншоти, відео та трейси;
- `allure-results/` - сирі результати Allure.

Згенерувати Allure HTML:

```bash
pnpm run report:allure
pnpm run report:allure:open
```

## Як продемонструвати баги на іншій сторінці

Опційна демонстрація навмисно відокремлена від основного набору тестів. Її цілі:

- UI: `https://with-bugs.practicesoftwaretesting.com`;
- API: `https://api-with-bugs.practicesoftwaretesting.com`.

Основна команда `pnpm run test` ніколи не виконує `tests/defects`.

Запустити сценарії навмисно зламаної сторінки та API:

```bash
pnpm run test:with-bugs
```

`test:defects` збережено як псевдонім:

```bash
pnpm run test:defects
```

Очікується, що команда повертає ненульовий код виходу, поки продемонстровані баги існують. Усі чотири сценарії все одно виконуються та створюють докази. Відкрити їхній окремий звіт:

```bash
pnpm run report:with-bugs
```

Опційний звіт записується в `playwright-report-with-bugs/`; скриншоти, відео та трейси — в `test-results-with-bugs/`. Він ніколи не перезаписує основний звіт.

Опційний Allure-звіт:

```bash
pnpm run report:allure:with-bugs
pnpm run report:allure:with-bugs:open
```

Після виправлення продемонстрованого бага його звичайна перевірка стає `passed`.

## Конфігурація

Основні URL можна перевизначити без змін у коді:

```powershell
$env:PST_UI_URL = 'https://practicesoftwaretesting.com'
$env:PST_UI_API_URL = 'https://api.practicesoftwaretesting.com'
$env:PST_API_URL = 'https://api-v2.practicesoftwaretesting.com'
pnpm run test
```

URL опційної демонстрації:

```powershell
$env:PST_BUG_UI_URL = 'https://with-bugs.practicesoftwaretesting.com'
$env:PST_BUG_API_URL = 'https://api-with-bugs.practicesoftwaretesting.com'
pnpm run test:with-bugs
```

Кожна команда очищає лише власні згенеровані папки звітів перед виконанням. Тому основний звіт і звіт опційної демонстрації залишаються незалежними й ніколи не накопичують застарілі результати.

## Docker

```bash
docker compose run --rm tests
```

Docker запускає основний набір тестів обраного ресурсу в усіх трьох браузерних проєктах (chromium, firefox, webkit — базовий образ уже містить їх усі) і генерує звіти Playwright та Allure. Опційна демонстрація навмисно зламаного середовища не входить до типової Docker-команди.

## CI

Workflow GitHub Actions розташований у корені репозиторію (`.github/workflows/playwright-finalproject.yml`) і запускається пушами та pull request'ами, які зачіпають `FinalProject/**` (плюс ручний `workflow_dispatch`), тому запуски з'являються лише для змін цього проєкту.

Workflow має дві джоби:

- `lint` — перевірка форматування Prettier, ESLint і перевірка типів TypeScript;
- `test` — основний набір тестів обраного ресурсу як матрична джоба `fail-fast: false` для кожного браузера (`chromium`, `firefox`, `webkit`), тож падіння одного браузера не скасовує інші. Кожна матрична джоба встановлює лише свій браузер, виконує `playwright test --project=<browser>`, генерує Allure-звіт і завантажує Playwright HTML-звіт та Allure-звіт як окремі артефакти.
